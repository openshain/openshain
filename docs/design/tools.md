# `@openshain/tools` の設計

標準 Tool は、Runtime が model に見せる何ができるかの一覧です。model は Tool を呼ぶ提案をするだけで、入力の検証、許可、実行、記録は Runtime(core)がやります。標準 Tool は 8 つです。fs_list、fs_search、fs_read、fs_write、csv_read、csv_aggregate、csv_write、markdown_read。Office 文書と Email は後の版で追加します。

標準といっても、Runtime から見れば第三者の Tool と同格です。同じ ToolProvider のインターフェースを通り、同じ許可リストに従い、同じ path guard を通ります。標準 Tool だけが使える Runtime の入口はありません。

## 結果は観測であって転送ではない

決めたこと。観測する Tool(fs_list、fs_search、fs_read、csv_read、csv_aggregate、markdown_read、knowledge_search、knowledge_read)は、依頼された範囲だけを返します。結果の先頭に JSON で件数と範囲と続きの有無を置き、本文はその後に続けます。既定の範囲は小さく、続きは `offset` と `limit` で model が取りに行きます。数値は spec の表にあります。

理由。context に入れたものは、そのターンだけでなく以後の全ターンで毎回入力として送られ、課金され、注意を薄めます。架空の会社の 296 行の CSV を、同じ model に同じ依頼文で依頼して測りました。csv_read が全行を返す版では Tool の結果 1 つが 48,115 文字あり、Work 全体の入力が 68,346 トークン、出力が 7,326 トークンでした。範囲と集計に変えた版では、同じ依頼が入力 30,985 トークン、出力 2,169 トークンで終わり、結果の数字は一致しました。出力が 3 分の 1 になったのは、model が行を読み上げながら足し算していたのをやめたからです。

捨てた案。

- 全行を返し、Runtime の 50,000 文字の切り詰めに任せる案。切り詰めは事故を止めるもので、context を守る設計ではありません。切られた行は model からも見えなくなり、合計が黙って欠けます。
- Tool の側で要約して返す案。要約は解釈で、model が読み間違えたときに元へ戻れません。範囲と件数なら、model が自分で続きを取れます。
- 投影の圧縮(古い Tool の結果を畳む)で対処する案。圧縮は後の版で入れますが、入ったあとも最初から小さいほうが安く、再現もしやすいです。

変える条件。変えません。context が安くなっても、転送は観測に戻せません。

## 数える、合計する、探すは Tool がやる

決めたこと。csv_aggregate(`group_by`、`sum`、`filter`)と fs_search を持ちます。model が行を読んで足す道は、csv_read と fs_read の説明文で塞ぎます。合計には csv_aggregate を使え、と書いてあります。

理由。model の足し算は毎回同じ結果にならず、検証もできません。Tool の集計は同じ入力なら同じ結果で、テストで固定できます。数字は Runtime の側で作り、model は表に写すだけにします。

集計の形。グループごとの行数と、`sum` に挙げた列ごとの sum、min、max、数値だった件数、数値でなく飛ばした件数を返します。`overall` に、条件に合った全行の同じ値を付けます。グループ別の値だけを返していたとき、model は 10 グループの和を自分で合計して総計を 10 万円間違えました。総計も Tool が返せば、足し算は起きません。飛ばした件数を返すのは、`n/a` や空欄が混じった列で合計が静かに欠けるのを model に見せるためです。`1,200` や `¥300` を数値として読むのは、日本の台帳ではその書き方が普通だからです。無い列を指定されたら、列名の一覧を `isError` で返します。列名を推測させるより、見せて選ばせるほうが呼び出し回数が減ります。

捨てた案。SQL や式言語を受け取る汎用の集計 Tool。強力ですが、model が書いた式の検証が難しく、注入の入口にもなります。形を固定した Tool のほうが、後で権限の判定(どの列を読んでよいか)にも載せやすいです。

変える条件。`group_by` と `sum` で足りない集計が具体的に現れたとき、Tool を 1 つ追加します。

## 説明文は出力の意味まで書く

model が Tool について読めるのは、名前、説明、入力 schema の 3 つしかありません。だから説明文には、何を返すか、何を返さないか、代わりに何を使うかまで書きます。返す形を変えたら説明文も変えます。説明文は model が読む文なので英語で書き、利用者向けの文言は CLI が持ちます。

## 出典を付ける

観測する Tool は `observation` を返し、Runtime が `tool.completed` に残します。結果が何をいつ見たものかを後から辿るためです。1 回の呼び出しが複数の出典を引くことがあるので一覧で、ファイルなら path と読んだ時刻、知識なら Source の id と取得日と版です。

## 知識は索引を通してだけ引く

決めたこと。`knowledge_search` と `knowledge_read` は、`knowledge/build/` に索引がある会社フォルダでだけ Tool の一覧に現れます。どちらも、依頼する人の principal と職種、会社の業務日で絞ってから答えます。読めないものは結果にも件数にも出さず、id を直接渡した読み取りにも「見つかりません」とだけ返します。索引が入力と食い違えば、内容を返さず build を促します。照合は Work ごとに 1 回です。

理由。索引が無いのに Tool を出すと、社員エージェントは呼んで失敗し、人には「決まりが無い」と映ります。無いのではなく作っていないので、出さないほうが正直です。絞り込みを Tool の中で行うのは、これが実行の可否ではなく返す内容の選別だからです(spec/knowledge.md)。読めない理由を言い分けない(無い、期間が終わった、他人のもの、を区別しない)のは、区別すること自体が「ある」と伝えるからです。役(`roles`)で書かれた scope は、`principals/` に書かれた人の `roles` から解決します。誰も書かれていない会社フォルダでは、役を持つ人がいないので誰にも見えません。開くより閉じるほうを選びました。`knowledge build` は、scope に書いた人と役が実在するかを確かめます。役の綴りを間違えると、誰にも読めない決まりが黙って出来上がるからです。

## workspace の外に出ない

決めたこと。すべての Tool が core の path guard を通します。相対パスだけを受け、`..` と絶対パス、symlink の先が外を指すもの、予約パス(`openshain.yaml`、`work/`)、先頭が `.` の項目を拒否します。判定は大文字小文字を区別しません。書き込みは O_NOFOLLOW で開きます。fs_list と fs_search は隠し項目と予約パスを見せません。

理由。パスは model が書く入力で、信用しません。`.git`、`.env`、Runtime 自身の記録には Tool からアクセスさせません。symlink を 1 段ずつ辿って行き先で判定するのは、workspace 内のリンクから外へ抜ける経路を閉じるためです。読めないものを一覧に出さないのは、model が読もうとして拒否され、呼び出し回数を無駄にするからです。

## 範囲は入口と一覧の 2 か所で効く

決めたこと。人ごとの範囲(`principals/<id>.yaml` の `reads`)は 2 か所で効きます。1 つは呼び出しの入口です。path を持つ呼び出しは、Runtime が範囲の外だと判定した時点で、ファイルに触る前に断ります。返す言葉は、そこに何かがあってもなくても同じです。もう 1 つは一覧と検索の中です。返す項目を絞り、件数も返した分だけにし、範囲に届かないフォルダには入りません。Tool には「その path は範囲の中か」「そのフォルダの下に範囲があるか」の 2 つの述語だけを渡します。Tool は規則も人も知りません。

理由。入口で断れば、`fs_read`、`csv_read`、`markdown_read`、`csv_aggregate`、`fs_write`、`csv_write` が 1 か所で揃います。Tool ごとに書くと、1 つ書き忘れた Tool が穴になります。ファイルに触る前に断るのは、触ると「大きすぎる」「フォルダではない」といったエラーが先に出て、範囲の外のことを伝えてしまうからです。返す言葉を実在で変えないのは、名前を正確に当てた人にだけ違う返事をすると、当てる経路になるからです。記録には本当の理由(`out_of_range`)が残るので、設定を直す人は原因にたどり着けます。止めている相手は社員エージェントで、人ではありません。会社フォルダを直接読める人は、この範囲の外です。

一覧と検索だけが中で絞るのは、返すものが 1 つではないからです。フォルダに入らないのは、入って全部捨てるのが無駄だからです。返事の遅さからも、そこに何かがあると読み取れます。

## 上限は 2 段

1 MiB を超えるファイルは開きません。Tool の結果は Runtime が 50,000 文字で切ります。範囲の制限が context を守り、上限が事故を止めます。役割が違うので両方あります。書き込みも同じ 1 MiB で止め、Tool が書いたものは Tool が開ける形にしてあります。

変える条件。1 MiB は経理の CSV と Markdown を確認して決めた値で、Office 文書を追加するときに見直します。

## 書き込みは直接、ただし記録する

決めたこと。fs_write と csv_write は今は直接書きます。結果に `after`(path と sha256)を返し、Runtime が記録します。Work の完了時に Runtime がファイルからハッシュを計算し直し、model の申告と食い違っても Runtime の値が残ります。

理由。提案、差分、承認、適用の順に進める ChangeSet は後の版で入れます。今の版で直接書いてよいのは、書き先が workspace の中に限られているからです。外部の SaaS に書く Tool はこの形では追加しません。

変える条件。ChangeSet が入ったら、`effect: "mutate"` の Tool はすべてそこを通します。`effect` はその差し込み口として今から付けてあります。

## CSV の数式を無害化する

csv_write は `=`、`+`、`@` で始まるセルに `'` を付けます。`-` で始まるセルは負数を除いて同じ扱いです。利用者は書いた CSV を Excel で開きます。model の出力に紛れた式がそこで実行されるのを防ぎます。

## 同じ入力には同じ出力

fs_list と fs_search はコードポイント順、csv_aggregate のグループはグループの値の順に並べます。locale に依存する並びは使いません。投影が byte 単位で再現できることが Runtime の前提で、Tool の結果もその一部です。テストが機械を選ばなくなります。

## パターンは wildcard、正規表現は受け取らない

決めたこと。fs_list と fs_search の `pattern` は `*` と `?` だけを特別に扱い、他の文字はそのまま照合します。照合器は 2 ポインタ法で、パターンと文字列の長さの積に比例する時間で必ず終わります。

理由。パターンは model が書きます。正規表現にすると、`.*a.*a.*a.*c` のような入れ子のない式でも 1,000 文字の行に 10 秒以上かかり、Tool の呼び出し 1 つで Work が止まります。最初は safe-regex2 で検査した正規表現を許していましたが、その検査は入れ子の量指定子しか見ず、この形を通しました。glob を正規表現に変換していた fs_list も同じ理由で止まりました。

捨てた案。走査を Worker に渡して期限で打ち切る案。動きますが、ファイルと仕組みが 1 つ増え、期限の値をどう決めるかが残ります。線形時間の照合器なら期限が要りません。

変える条件。wildcard で書けない検索が具体的に現れたとき、線形時間の正規表現エンジンを依存に追加するかを考えます。バックトラックする正規表現を model に書かせる形には戻しません。Tool 定義の schema にある `pattern` は core が検査しますが、あれは Tool の作者が書く固定の式で、事情が違います。

## 公開 API

export するのは `standardTools()`、`MAX_READ_BYTES`、`MAX_WRITE_BYTES`、`DEFAULT_WINDOW` です。Tool の中の関数は公開しません。標準 Tool を拡張したい人は provider を 1 つ追加し、設定で並べます。provider の組み合わせは設定で決めるものだからです。

## 捨てた案(package 全体)

- Tool の種類ごとに package を分ける案(fs、csv、markdown)。今は 1 ファイルで足ります。分けるのは Office 文書で依存が増えたときです。
- Node の fs の前に抽象 FS を挟む案。差し替える実装がありません。

## これから

Office 文書(xlsx、docx、pdf)と Email です。表は csv_read と同じ範囲の指定と集計で読めるようにし、文書は markdown_read と同じ見出しと節で読めるようにします。形式ごとに別の読み方を model に覚えさせません。
