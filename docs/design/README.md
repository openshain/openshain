# 設計ノート

spec は何を作るかを決め、このディレクトリはなぜその形にしたかを残します。package ごとに 1 本です。決めたこと、理由、捨てた案、その判断を変える条件を書きます。現状を書き換えて保つ文書で、履歴は git に任せます。

| package | ノート | 一言で |
|---|---|---|
| `@openshain/core` | [core.md](core.md) | インターフェースとイベントログです。判断はコードが持ちます |
| `@openshain/agent` | [agent.md](agent.md) | イベントログの上で回る tool loop と、インターフェースに揃える provider です |
| `@openshain/tools` | [tools.md](tools.md) | 標準 Tool です。結果は観測であって転送ではありません |
| `@openshain/mcp` | [mcp.md](mcp.md) | 外部エージェントが考え、Runtime が状態と記録を持ちます |
| `openshain` CLI | [cli.md](cli.md) | 参照実装のクライアントです。見せるのは進捗と結果だけです |

## package をまたいで守ること

各ノートは次の 5 つを前提にしています。

1. インターフェースは core に置き、公式実装も第三者実装も同じインターフェースを使います。core に公式向けの裏口を作りません。
2. 金額、権限、状態遷移、安全の判定は普通のコードで書きます。model の出力に判断を委ねません。
3. Work の原本は `work/<id>/events.jsonl` です。会話履歴も進捗も使用量も、そこから組み立てます。別の保存形式を持ちません。
4. model に渡すのは、目的に合わせて組み立てた投影です。ファイルや履歴を丸ごと渡しません。
5. 外部への効果(ファイルの書き込み、API の呼び出し)は Runtime が検証し、記録してから次へ進みます。

## ノートの書き方

- 節ごとに、決めたこと、理由、捨てた案、変える条件の順で書きます。理由は工学の言葉で書きます。context の大きさ、再現性、事故の防ぎ方、テストのしやすさです。
- 既定値と上限の数値は spec が正です。ノートには理由だけを書きます。数値を変えるときは spec とノートの両方を修正します。
- package の振る舞いを変える commit には、そのノートの更新を含めます。ノートと spec と実装が食い違ったら、どれを修正するか決めてから進めます。
