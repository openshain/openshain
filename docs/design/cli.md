# `openshain` CLI の設計

CLI は Runtime の参照実装のクライアントです。汎用のエージェント製品ではありません。MCP Server と同格の入口で、model は利用者の API キーで呼びます。

## 見せるのは進捗と結果だけ

決めたこと。`run` と `work resume` の進捗行は、Tool の呼び出し(名前と、path があればその値)、拒否(理由)、失敗の 3 種類だけです。model の呼び出しと質問の記録は出しません。最後に、状態、結果の要約、使用量の合計、次に動くのが誰か(利用者、model、なし)を出します。

理由。利用者が知りたいのは、何をしているか、何が終わったか、誰を待っているかです。model の思考の垂れ流しは、読む時間を取るわりに判断に使えません。

捨てた案。streaming で model の出力を流す案。進捗の代わりにはなりますが、記録の単純さ(agent のノート)を優先しました。

## 文言は表で持つ

状態、失敗の理由、拒否の理由、エラーの code の日本語は `labels.ts` の名詞句の表にあります。code は英語のまま裏に残り、表にない語はそのまま表示します。文言の変更がロジックに触れないためです。表示幅は文字幅で揃えます。日本語は 1 文字が 2 桁分あり、`padEnd` では列が崩れます。

## exit code は 3 つ

0 は完了です。1 は完了しなかった Work か実行時のエラー、2 は引数の誤りです。シェルから成否を判定できるようにしています。

## 端末がなければ質問しない

TTY がなければ `ask_user` に答えず、`waiting_input` のまま質問文を出して終わります。cron や CI から呼ばれた `run` が永遠に待たないためです。答えは端末のあるところで `work resume` します。

## 端末に出す文から制御文字を落とす

決めたこと。画面と `run` の出力は、改行とタブ以外の制御文字を落としてから端末に出します。model の返答、Tool の結果、ファイルの中身は端末にとって信用できない文で、escape sequence が混ざれば画面を消したり、窓の題を変えたり、端末によってはクリップボードに書いたりできます。見えない書式の文字(ゼロ幅と双方向の制御)も落とします。ファイル名の途中に右から左への制御が入ると、表示と実体が食い違うからです。落とす場所は出力の出口(`write`、質問の表示、画面の行)の 3 か所だけにして、文を作る側は気にしなくてよい形にしました。画面を出るときの端末の復帰(別画面とマウス報告の解除)は、正常終了、信号、描画中の例外のどの経路でも 1 回だけ書きます。

## `--workspace` と探索

`init` は指定したディレクトリに `openshain.yaml` のひな型を書きます。他のコマンドはそこから上に向かって `openshain.yaml` を探します。会社のフォルダのどこにいても同じ Work が見えるためです。

## 画面は社員エージェントとの会話で、作業は Work に出す

決めたこと。`openshain` と打つと社員エージェントと話す画面が開きます(spec/interactive-cli.md)。社員エージェントが持つ道具は `work_run`、`work_list`、`work_show` の 3 つで、ファイルを触るのは `work_run` が作る子 Work の中だけです。会話は `type: session` の Work として残り、子 Work は `parent` でそれを指します。画面は Ink で端末の全画面(alternate screen)に描き、上に会話、下に枠つきの入力欄と状態行を置きます。Codex CLI や opencode と同じ形で、入力欄が常に最下段にあり、履歴は画面の中で PageUp と PageDown と矢印で遡ります。行の折り返しと見える範囲は自分で計算します。Ink の overflow は上にはみ出した子を切れず、行が重なったからです。行の配列は差し替えで更新します。同じ配列に足すと React が変化を見落とします。入力欄は 1 行で、Ink は貼り付けをまとめて渡し、その中の改行は Enter 扱いにしないので、最初の改行までを送ります。上下の矢印は shell と同じ入力履歴です。会話を遡るのはマウスホイールと PageUp、PageDown で、端末にマウスの報告(SGR)を頼みます。ホイールを矢印として受け取る方式(alternate scroll)は入力履歴と衝突するので使いません。マウスの報告中は文字の選択に Shift が要る端末が多く、それは受け入れました。Claude Code は別画面を使わないので遡るのは端末の仕事ですが、openshain は別画面なので自分で持ちます。終了すると元の画面に戻って会話は端末に残らないので、記録の読み方を 1 行出します。子 Work が終わると、CLI と同じ締めの行(書いたファイル、使用量、次に動くのが誰か)を進捗行と同じ扱いで出し、要約は社員エージェントの返答に任せます。同じ文を 2 度読ませないためです。Ctrl-C は動いているものを止めます。子 Work なら `in_progress` のまま、質問を待っていれば質問を取り下げて `waiting_input` のまま残し、どちらも `/work resume` で続きます。閉じるとき(`/quit`、SIGHUP、SIGTERM)も同じ手順で止めてから記録を閉じます。セッションの lock は社員エージェントのターンが持っているので、止めずに閉じようとすると lock に阻まれて記録が `in_progress` のまま残ります。

理由。会話は続きますが、記録が要るのは作業のほうで、作業は 1 つの依頼から終わりまでを単位にしたいからです。社員エージェントに作業を委ね、子 Work が自分の loop と Tool で動く形なら、社員エージェントは今どの Work の中かを持たずに済み、記録は Work ごとに閉じたままになります。Ink を選んだのは、採用例(Claude Code、Gemini CLI)が多く更新が続いていて、Bun で動き、単体バイナリにもできることを確かめたからです。

捨てた案。

- 社員エージェントがファイルの Tool を直接持ち、`work_create` で現在の Work を決めて括る案(MCP server の形)。接続ごとに Work が 1 つの MCP では成り立ちますが、社員エージェントが同時に 2 つの作業を始めると呼び出しの帰属が決まりません。
- 全画面ではない readline の対話。依存は増えませんが、進捗、質問、入力欄を 1 画面に同居させると行の出力だけでは崩れます。
- 会話を端末に流して残し(Ink の Static)、下に入力欄を置く Claude Code の形。端末のスクロールバックとコピーがそのまま効きますが、入力欄が最下段に固定されず、会話の画面としては弱いです。
- セッションを別の記録(`sessions/`)にする案。概念はきれいですが、envelope、lock、一覧、schema をもう 1 組作ることになります。type で区別して Work の仕組みを使い回しました。

変える条件。並行して作業を進めたくなったら、すぐ返る `work_start` と後で見る `work_status` を社員エージェントの道具に足します。閉じたセッションを再開したくなったら、そのときに spec を切ります。

## スラッシュコマンドは 2 種類

決めたこと。組み込みコマンド(`/work …`、`/tools`、`/help`、`/quit`)は CLI が解釈して model を通しません。それ以外は prompt コマンド `/{名前} {文}` で、`{文}` は自由な文のまま社員エージェントに渡し、解釈は model に任せます。prompt コマンドは職種 Pack のスキル、workspace の `skills/`(Agent Skills の形式)、MCP server の prompt から集めます(spec/interactive-cli.md)。

理由。記録の状態を変える操作(Work の再開)は、どの Work かを正確に取りたいので、CLI が引数を解釈します。一方、拡張できるコマンドは Claude Code の custom command、Agent Skills、MCP の prompt がどれも「名前と文」の形で、文の解釈を model に任せています。同じ形にしておけば、それらをそのまま載せられます。MCP の prompt だけは引数に名前があるので、語順で当ててから server に展開させます。

捨てた案。組み込みコマンドの引数も model に解釈させる案。「さっきの集計のやつ」と言えるのは便利ですが、取り違えた再開は記録に残ります。id の一覧を見せて選ばせるほうが確実です。

## `init` は 4 つのファイルを書く

決めたこと。`openshain init` は `openshain.yaml` のほかに、Claude Code 用の `.mcp.json`、外部エージェントへの指示の `AGENTS.md`、それを読ませる `CLAUDE.md` を書きます。`openshain.yaml` があれば断り、他の 3 つは無いものだけ書きます。

理由。Claude Code からの接続テストで詰まったのは、`.mcp.json` を手で書くことと、依頼文で自前の Tool を使わないよう言わないと Runtime を通らないことの 2 つでした。どちらも会社フォルダにファイルを 1 つ置けば済みます。`.mcp.json` の command が `openshain` で済むのは、配布をバイナリにして PATH に置く形にしたからです。

捨てた案。指示を `openshain.yaml` の `profession.instructions` に入れる案。あれは Runtime が model に渡す文で、外部エージェントは読みません。

## `openshain mcp` を同梱する

MCP Server は別 package ですが、起動は CLI のサブコマンドです。インストールを 1 回で済ませるためです。

## 捨てた案

- 色付け。端末によって崩れ、テストが読みにくくなります。
- 使用量の金額換算。単価表を持つと保守が要り、vendor ごとに変わります。トークン数だけを出します。

## 公開 API

配布物は `openshain` コマンドだけです。コマンドの関数は bin とテストのために export していますが、import して使うインターフェースではありません。予告なく変えます。プログラムから使うなら core と agent を使ってください。
