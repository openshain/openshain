# 設計ノート: 観測と義務

仕様は [spec/observations.md](../../spec/observations.md) です。ここには、なぜこの形にしたかを書きます。

## 事実は書き換えない

決めたこと。観測(`observations/<id>.json`)は 1 件 1 ファイルで、後から書き換えません。間違いに気づいたら新しい観測を書きます。

理由。観測は「起きたこと」です。起きたことは後から変わりません。書き換えられる事実は、あとで記録を読む人にとって事実ではなくなります。Work のイベントログが追記だけなのと同じ考え方です。

## 対応は Work の側に残す

決めたこと。観測と Work の対応は、`work.created` に観測の id と義務の id を書く形で残します。観測のファイルに Work の id を書き足しません。

理由。書き足すには観測を書き換えることになり、上の決めごとと衝突します。Work は最初から「なぜ自分が在るか」を持つほうが自然でもあります。「この観測から何が始まったか」を知りたいときは Work を引きます。会社フォルダ 1 つぶんの件数なら、それで足ります。

## 観測と義務は Tool から触れない

決めたこと。`observations/` と `obligations/` を予約パスにしました。

理由。社員エージェントが観測を書けると、事実と作り話の区別がなくなります。自分で「請求書が届いた」と書いて、自分でその仕事を始められます。義務を書けると、自分の仕事を自分で決めることになります。どちらも人が書くものです。`authority/` を予約にしているのと同じ理由です。

## 引き金は 1 種類だけ入れる

決めたこと。この版の引き金は `event`(この type の観測が来たら)だけです。時刻の引き金(月末の 3 日前)と条件の引き金(30 日以上未払い)は入れません。

理由。時刻と条件の引き金には、時間が経ったことに気づく仕組みが要ります。常駐するものが無い今それを書くと、呼ばれる当てのないコードになります。観測から始まる引き金は、観測を記録した瞬間に判定できるので、いま完結します。3 種類を「統一的に扱う」形にするのは、常駐の仕組みが入る版です。

## 記録が先、仕事が後

決めたこと。`observe` は観測を先に書き、そのあとで義務を読んで Work を作ります。義務が 1 つも無い会社フォルダでも、観測は残ります。

理由。事実を残すことと、それに対して何をするかは別のことです。義務の書き方を間違えていても、起きたことは失われません。あとから義務を足して、同じ種類の次の観測から効かせられます。

## 名前

`Observation` は Fundamental Object の名前です。Tool の結果に付く出どころ(`{ source, retrievedAt }`)は、同じ語を使っていたので `ToolObservation` に変えました。項目名(`observation`)は変えていないので、第三者の Tool には影響しません。1 つの package に同じ名前の別のものが 2 つあると、読む人がどちらか分かりません。
