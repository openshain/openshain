# 会社に人が複数いるときの、見える範囲

会社に人が 2 人以上いるとき、社員エージェントが誰の代理で何を見るかを決めます。1 人の会社フォルダは、これまでとまったく同じに動きます。

## 覚えてもらうこと

> 社員エージェントは、依頼した人の担当の範囲で働きます。渡していない場所は、その人にとって無いのと同じです。

出てくるのは「誰が」と「どこを」の 2 つだけです。

## 得られないもの

先に書きます。

- **認証はありません。** 会社フォルダを開ける人は、誰を名乗ることもできます。名乗りの選択であって、本人確認ではありません
- **記録と権限と知識の生ファイルは、フォルダを直接読める人には読めます。** ここで絞り込むのは openshain の Tool を通る経路だけです
- **同時に使うことは、この版でも想定していません。** 同じ会社フォルダを 2 か所で同時に動かすと、記録が同期の競合として分かれます。順番に使ってください

得られるのは、社員エージェントが担当の外をうろつかないこと、渡す相手を間違えないこと、記録に誰の依頼かが残ること、認証が載ったときに書いた表がそのまま効くことです。悪意のある同僚を止める鍵ではなく、事故を止めるシートベルトです。

## 人を置く(`principals/<id>.yaml`)

```yaml
id: bob                           # ファイル名と一致すること
name: Bob
roles: [accounting]               # 会社が決める言葉。openshain は比べるだけ
status: active                    # active か inactive。既定は active
reads: [ledger/**, receipts/**]   # 見える範囲。書かなければ全部
records: own                      # own か all。reads を書いた人の既定は own
```

1 人 1 ファイルです。入った日と外れた日が git の履歴に残ります。外すのは `status` の 1 行です。`principals/` が無ければ、`openshain.yaml` の principal が 1 人いるだけの、これまでの状態です。

`roles` は担当を表す会社の言葉です。資格者の `reviewer.role`(税理士など)とは別のもので、混ざりません。

### 読み込み

- `<id>.yaml` の形でないファイル名は読みません。クラウドの同期が作る `bob (conflicted copy).yaml` のようなファイルで、会社の判断が止まらないようにするためです
- ファイル名と中の `id` が違うとき、YAML が壊れているときは、起動しません。開くのではなく閉じます。ファイル名がその人なので、2 つのファイルが同じ人を名乗ることはできません
- 判定のたびに読み直します(`authority/` と同じ)。`inactive` にした瞬間から、開いたままの会話にも効きます

## 誰として働くか

```
openshain --principal bob        # この端末は bob として使う
OPENSHAIN_PRINCIPAL=bob openshain
```

`.mcp.json` から使うときは `env` に書きます。Claude Code は `openshain mcp` を自分で起動するので、フラグでは届きません。

- 指定が無ければ `openshain.yaml` の principal です
- **`reads` を書いた人が 2 人以上いるのに指定が無いときは、起動せず、名前を挙げて選ばせます。** 黙って別の人として動くのが、いちばん起きてほしくないことだからです
- 指定した id が `principals/` に無い、または `inactive` なら起動しません
- 起動時の 1 行に「bob として実行します。本人確認はしていません」と表示します

## 見える範囲(`reads`)

順序のない集合です。上から読む表ではないので、前の行が後の行を隠すことも、綴りを間違えて範囲が広がることもありません(間違えれば狭くなるだけです)。

- `fs_list` は範囲の外の項目を返しません。件数も返した分だけです。隠した数は返しません
- `fs_search` は範囲の外のファイルを探索の対象から外します。`filesSearched` などの数にも入れません。範囲に一致しないフォルダには降りません
- `fs_read`、`csv_read`、`csv_aggregate`、`markdown_read` は、範囲の外のパスを読みません
- **範囲の外を名指しされたときは、そこに何かがあるかどうかに関わらず、同じ返事をします。** 実在するものだけ違う返事をすると、名前を当てる経路になります
- **書き込みも範囲の外には届きません。** 読めない場所に書けてはいけません
- 判定は、ファイルを開く前に行います。大きさや `ENOTDIR` のエラーが先に返ると、範囲の外のことが伝わってしまいます
- 記録には、どの範囲の外だったかという本当の理由が残ります。モデルに返す言葉と、記録に残すことは別です

`reads` と `authority/policy.yaml` は別の質問に答えます。`reads` が「見えるか」、表が「実行してよいか」です。`reads` は上限です。範囲の外を表が `allow` しても届きません。その組み合わせは設定の誤りなので、`openshain principal check` が報告します。

## 記録(`records`)

`own` と書いた人には、次の Work だけが `work_list`、`work_get`、`approval_list`、`openshain work show` に現れます。

- 自分が依頼した Work
- **自分が承認者か資格者として名指しされている Work**。承認は他人の仕事に対して行うものなので、これが無いと承認待ちが誰にも見えなくなります

`reads` を書いた人の既定は `own` です。`reads` を書いていない人の既定は `all` で、これまでと同じです。

見える Work の中身も、閲覧者の範囲で絞ります。**path とハッシュだけでなく、呼び出しの入力と結果も伏せます。** 書き込んだ本文や読み取った中身が入っているためです。`approval_list` が返す呼び出しの入力も同じです。

`work_select` が他人の Work を拒否するときは、所有者の名前を返しません。

## 役割(`role`)

`authority/policy.yaml` の `match` に `role` を足します。依頼した人がその役割を持つときに一致します。

```yaml
- id: ledger-writes-need-approval
  match: { role: accounting, tool: [fs_write, csv_write], path: "ledger/**" }
  decision: approval_required
  approvers: [alice]
```

`knowledge` の `scope: { roles: [...] }` が解決できるようになります。いまは誰にも見えません。`knowledge build` は、`scope` に書いた principal の id と role が `principals/` に実在するかを確かめます。綴りを間違えて、誰にも見えない決まりができるのを防ぐためです。

## `inactive`

- 委任が効きません。`delegations.yaml` に残っていても通りません
- 承認者にできません。判定のたびに読み直すので、開いたままの会話にも効きます
- `--principal` で名乗れません
- その人の記録は残り、読めます

## 検査(`openshain principal check <id>`)

その人に何が見えて、何ができるかを 1 回で示します。

- `reads` に実際に一致するファイルとフォルダ(件数つき)。glob の綴り間違いは、ここで見つかります
- 委任があるか。委任が無ければ、その人は何も実行できません
- `role` で一致する規則
- `reads` の外を `allow` している規則(設定の誤り)
- `records` の設定と、見える Work の件数

## 完了の条件

1. `principals/` が無い、または `reads` を書いていない会社フォルダは、これまでと同じに動きます
2. 範囲の外のファイルが、一覧にも検索にも件数にも現れません
3. 範囲の外への書き込みが届きません
4. 範囲の外を名指ししたとき、実在するかどうかで返事が変わりません。記録には本当の理由が残ります
5. `records: own` の人には、自分の Work と、自分が承認者に名指しされた Work だけが現れます。見える Work の中身も、範囲の外は入力と結果ごと伏せます
6. `inactive` にした瞬間から、開いたままの会話でも委任が通らず、承認もできません
7. `scope: { roles: [...] }` の資料が、その役割を持つ人にだけ見えます
8. 実在しない id か role を書いたとき、読み込みか `knowledge build` が拒否します
9. `--principal` の id が無いか `inactive` なら起動しません。`reads` を書いた人が 2 人以上いて指定が無いときも起動しません
10. 同期の競合が作ったファイル名では、判定が止まりません
11. 社員エージェントが、範囲の外を繰り返し試しません(実際のモデルで確かめます)
